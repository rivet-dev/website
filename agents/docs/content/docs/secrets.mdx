## Why the token stays private

An agent works across three places: the model at its provider, the agent Actor on your worker, and the sandbox where the built-in file and shell tools run. `get_order` is a custom tool, so it runs in the agent Actor, next to the rest of your server code.

When the model looks up an order:

1. The model sends a tool call with the name `get_order` and the argument `orderId`.
2. The agent Actor runs `execute` on your worker. It reads `ORDERS_API_TOKEN` from the worker's environment and calls your API.
3. The tool returns a one-line summary. That text is the tool result the model reads.

| | Sees the token |
| --- | --- |
| Your tool code | Yes, from `process.env` on the worker. |
| The model | No. It sees the tool's name, description, parameters, and results. |
| The session and connected clients | No. The session stores tool arguments and results, and streams them to every connected client. |
| The sandbox | No. Commands run with the sandbox's own environment. If the model runs `echo $ORDERS_API_TOKEN` with `bash`, it prints nothing. |

Tool results and error messages are stored in the session and sent to clients, so keep secrets out of both.

## Things to know

- Set `ORDERS_API_TOKEN` wherever your worker runs, like any other server secret.
- A tool doesn't receive the agent's key, so it can't choose a different secret per user or tenant.
- Model keys work differently. See [API Keys](/agents/docs/api-keys).
